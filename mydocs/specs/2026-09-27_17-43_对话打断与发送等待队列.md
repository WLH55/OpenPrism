## 1. Requirements (Context)

- **Goal**:
  1. **打断**：AI 输出过程中，发送按钮变为「停止」按钮，点击可中止当前回合（停止模型调用与输出，已收到的部分输出保留）。
  2. **等待队列**：AI 输出过程中输入的新消息不直接发送，而是进入输入框上方的等待队列；每条可：
     - **立即发送**（中止当前输出，立即发出这条消息）；
     - **等待自动发送**（默认行为：AI 输出完成后自动按入队顺序发送）；
     - **删除**（取消这段文字，不发送）。
- **In-Scope**:
  - 服务端：`POST /api/conversations/:cid/stop` 打断端点（复用 harness `agent.cancel()`）；`send()` / `/stream` 的会话归属（ownerOf）校验补齐。
  - 前端：`generating` 状态机（SSE `status`/`turn-end` 事件驱动）；发送按钮三态变形；等待队列状态 + UI + 自动出队；中止消息「已中止」标记；切换会话清理 stream/队列（顺带修 stream 残留 bug）。
  - 测试：上述服务端行为的确定性测试（mock adapter，零网络）。
- **Out-of-Scope**:
  - harness 循环机制改动（`cancel()` 已具备所需语义，零改动）。
  - 队列跨设备 / 刷新持久化（队列是浏览器内存态，刷新即清空——消息尚未发出，不涉及日志重建）。
  - 语音输入、多端打断、服务端排队 API。
- **Acceptance Criteria**:
  - [ ] AC1 打断：AI 输出中（输入框为空）发送按钮呈「停止」；点击后当前回合以 `reason=aborted` 结束，已收到的部分输出以 `interrupted: true` 落日志并在气泡上标「已中止」。
  - [ ] AC2 队列：AI 输出中发送的新消息进入输入框上方队列（不直接进会话）；AI 回复完成后按入队顺序自动发送。
  - [ ] AC3 队列操作：队列条目可「立即发送」（先中止当前输出再立即发出）与「删除」。
  - [ ] AC4 归属：非本人会话的 `stop` / `send` / `stream` 一律 404 且无副作用。
  - [ ] AC5 回归：`pnpm typecheck` 与 `pnpm test` 全绿（319 既有 + 新增）。

## 2. Research Findings

- **事实与约束**:
  - harness 已有完整打断能力：`Agent.cancel(options?)` 中止当前 Turn（`AbortController`），已收到的增量（含思维链）组装为 `interrupted: true` 的 assistant 消息落日志，`turn/end{reason:"aborted"}` 收尾；默认 `clearInbox: true` 会清服务端 Inbox（`src/harness/core/agent.ts:426`）。本任务**零 harness 改动**。
  - 服务端 `POST /messages` → `conversations.send()` → `agent.followup()` 立即返回 202，回合在后台跑；agent 忙时 followup 进服务端 Inbox，作为下一 Turn 开场（服务端天然有排队，但无法「删除」）。
  - SSE `/stream` 连接时先推一条 `{type:"status", status: agent.status}`，此后 `status: running / idle` 全程广播（`src/app/server.ts:549`）；前端 `Chat.tsx` 目前**忽略** status 事件，没有 generating 状态。
  - mock adapter 的 `fn` 步骤可 `onTextDelta` 后挂起并监听 `options.signal` 的 abort 再抛 `ABORTED`——中止路径可确定性测试。
  - 前端图标库无「停止」图标，需新增 StopIcon（实心方块）。
- **现状链路**（发送 → 输出）：`Chat.send()` 乐观插本地气泡 → `api.sendMessage`（202）→ SSE `text-delta/reasoning-delta` 增量 → `assistant`/`turn-end` → `loadEvents` 重放日志。打断只需在「按钮 → 新端点 → cancel()」补一段，队列是纯前端状态机。
- **风险与不确定项**:
  - **越权缺口（既有 bug，本任务顺带修）**：`POST /messages` 与 `GET /stream` 没有归属校验——登录用户可用他人 cid 向其会话写消息 / 订阅其直播流（003bfad 只修了 events 读端点）。`send()` 与 `/stream` 需加 `ownerOf` 检查，与新增 `/stop` 保持一致。
  - 自动发送触发时机依赖 SSE；EventSource 断线重连后服务端会重推当前 `status`，配合幂等守卫（仅 `!generating` 时出队）不会重复发送。
  - 「停止」后队列是否继续自动发送：设计选择**继续**（队列承诺是「AI 回复完成后发送」，中止也是完成）；用户随时可删除。

## 3. Innovate (Optional: Options & Decision)

### Option A：等待队列放客户端（浏览器内存态）
- Pros: 三个操作（立即发送/自动发送/删除）都是 UI 层动作，客户端最直接；不新增服务端排队/删队 API；不落日志（未发出的内容本就不该进会话日志）。
- Cons: 刷新页面丢队列（可接受——消息从未发出，用户损失的是「还没说的草稿」）。

### Option B：等待队列放服务端（复用 Inbox followup 排队）
- Pros: 刷新不丢；天然多端一致。
- Cons: 「删除排队消息」需新增撤销端点；排队中的消息对前端不可见（需再开查询端点）；与 harness Inbox 语义（steer/followup 通道）耦合，改动面大。

### Decision
- Selected: Option A（客户端队列）
- Why: 需求三操作全在 UI 层；实现面最小且不动 harness / 日志边界；服务端 Inbox 排队继续作为其他入口（定时任务、旧客户端）的兜底行为不变。

### Skip (for small/simple tasks)
- Skipped: false
- Reason: 队列位置是真实架构分叉，故保留两案对比。

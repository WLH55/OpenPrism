## 1. Requirements (Context)
- **Goal**: 用户在微信收到的每日简报等任务通知被截断（2026-11-04 真机实证：475 字符处断在半句话）——修复后任意长度文本完整到达微信与站内通知。
- **In-Scope**:
  - wechat-bridge.ts 全部出站文本发送路径统一改为「超限分段、永不裁剪」。
  - main.ts 任务推送链路删除 `.slice(0, 480)`（微信）与 `.slice(0, 500)`（站内）。
  - withContextNudge 保活提醒改为追加到完整文本末尾。
  - 配套确定性测试（vitest，fakeILink，零网络）。
- **Out-of-Scope**:
  - ilink.ts 协议层（无裁剪，不动）。
  - 前端通知 UI 展示样式（Tasks.tsx 的 CSS truncate 为展示态，数据完整即可）。
  - iLink 服务端真实硬上限的进一步实测（沿用聊天回复通道 4000 的长期真机证据）。
- **Acceptance Criteria**:
  - [ ] AC1 ≤4000 字符文本微信单条完整送达（含每日简报量级 ~600 字符，全文含标题）。
  - [ ] AC2 >4000 字符文本分段连续送达：各段 ≤4000 码点、按序拼接等于原文、emoji 等代理对不撕裂、段界优先落在换行处。
  - [ ] AC3 全部出站路径（任务推送、聊天回复、说明推送、欢迎语、媒体失败提示）无 slice 裁剪，不存在静默丢字。
  - [ ] AC4 站内通知（notifications 表）存任务回复全文。
  - [ ] AC5 withContextNudge 警告态（≥11h）在完整文本末尾追加引导句，正文不裁剪。
  - [ ] AC6 `pnpm test` 全绿 + `pnpm typecheck` 0 错误 + `pnpm build:web` 成功；提交、部署、健康检查通过。

## 2. Research Findings
- 事实与约束:
  - 截断链三道防御上限：`main.ts:212` `.slice(0, 480)`（最紧，实际生效）、`main.ts:209` `.slice(0, 500)`（站内）、`wechat-bridge.ts:48/50/510` `.slice(0, 500)`（被上游 480 提前截断，轮不到生效）。
  - 上限来源是防御性照抄 WeKnora（iLink 无公开长度文档）；聊天回复通道已放宽到 4000 并长期真机正常，证明 iLink 实际承载远超 500。
  - 调度器与任务链路成功时零日志、微信桥只在失败时输出——截断在日志层不可见（journal 近两天无 `[wechat]` 失败行 = 推送成功送达了裁剪文本）。
  - `ilink.ts` sendMessage（:230）无任何长度处理，文本原样进请求体。
  - notify.ts `push` 原样入库 `payload.text`，无长度约束；前端 Tasks.tsx 仅 CSS truncate 展示态。
  - `REPLY_MAX_CHARS` 为模块私有常量，测试无引用，可安全改名/换语义。
- 现状链路: taskRunner（main.ts）→ withContextNudge（裁 500）→ pushToWechat（裁 500）→ ilink sendMessage → iLink；出站调用点共 5 处 sendMessage（bridge :153/:189/:406/:419/:510），其中 3 处带 slice。
- 风险与不确定项: iLink 服务端单条消息真实硬上限未公开——缓解：段长取 4000 与聊天回复通道同口径（长期真机证据）；若未来真机发现超长单条被拒，下调单个常量即可。

### 4.1 File Changes

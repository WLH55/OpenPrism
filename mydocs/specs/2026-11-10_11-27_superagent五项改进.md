## 1. Requirements (Context)

- **Goal**: 五项相互独立的改进全部落地并通过全量测试：
  1. 微信通道接入 steer（运行中插话改向，inject 不接——应用层无信源）
  2. 悬空 tool_call 的投影级确定性补全（硬崩溃恢复）
  3. 压缩遮蔽区间可回读（read_shadow 工具 + checkpoint 区间标注 + 记忆条目 id 与链式查询）
  4. 到点任务按 feed 会话分组并发（组内串行保推送归属，组间并行）
  5. 回合级超时看护（超阈值 stop + 站内通知）
- **In-Scope**: `src/harness/session/project.ts`、`src/app/{conversations,wechat-bridge,tasks,main,memory,shadow}.ts`、`CONTEXT.md`、`docs/design/2026-09-harness.md`、对应测试文件
- **Out-of-Scope**: inject 通道接线（无事件信源）、Router/Worker 双层、语义过滤、压缩触发阈值可配置化（用户已决定不改）、滑动窗口（同前）
- **Acceptance Criteria**:
  - [ ] AC1 微信会话运行中收到的纯文本消息（无附件、无攒批媒体、无 `/` 前缀）以 channel=steer 进入当前回合并即时生效；微信推送为「插入点之后的增量文本」，多条插话不重复推送；带附件与 `/` 前缀消息仍走 followup 排链
  - [ ] AC2 含悬空 tool_call 的会话日志经 deriveMessages 后，每个悬空 tool_call 紧随一条 code=INTERRUPTED 的合成 isError 结果；日志零改动（投影确定性推导）；invariants 全绿
  - [ ] AC3 压缩 checkpoint 消息末尾带 seq 区间标注；read_shadow 工具按区间渲染原文（宽度上限、越界 isError）；`<user_memory>` 条目行带 id；search_memory 支持按 id 返回本条与 supersede 链邻接条目
  - [ ] AC4 同一 tick 内不同 feed 会话的到点任务并行执行（并发上界 3），同 feed 组内严格保序串行且 run 记录/推送归属正确；分发时即推 lastRun，任务挂起期间重复 tick 不重发
  - [ ] AC5 回合运行超过阈值（缺省 20 分钟，OP_TURN_MAX_MS 可覆盖）被 stop（abort 语义收尾）并落站内通知；未超时的运行回合不受影响

## 2. Research Findings

- 事实与约束:
  - Inbox 三通道机制完备（`agent.ts:98/227-234/441-465`）：followup 唤醒开新回合、steer 唤醒插入当前回合（空闲时作为开场输入，`agent.ts:458`）、inject 不唤醒；回合结束未消费的 steer 转 followup（`agent.ts:393`）；应用层只调 followup，steer/inject 零调用点。
  - `wechat-bridge.ts`：per-uid `turnChains` 串行链（:139/156）；`runTurn` 已有 `before = readAll().length` 水位 + `slice(before)` 增量提取回复的模式（:400/412）；带文本消息立即开回合并合并攒批媒体（:362-367）。
  - 悬空缺口：assistant/message（含 tool_calls）先落日志（`agent.ts:320-324`）、tool/result 后落（:360-383）；abort/预算/管线错误路径均补合成结果，唯独进程硬崩溃落在两者之间时无修复；投影层（`project.ts:105-152`）对悬空 tool_call 无处理，重启后 wire 请求带悬空 tool_calls 会被 OpenAI 兼容端点 400 拒绝。日志 append-only，无法回插；投影确定性推导是 AGENTS.md 铁律 2 认可的第二条路径。
  - 压缩：`compaction/summary` 事件携带 `shadowed [start,end]`（`project.ts:133-147`）；checkpoint 消息（`summaryCheckpointMessage`，:93）不带区间信息；遮蔽原文在日志里永续存在但无取回工具。
  - 记忆：`MemoryItem.supersededBy` 链存在（`memory.ts:82`）；`renderEntry` 行格式 `- (标签) 内容` 不带 id（:575-578）；`searchMemory` 仅词法/向量（:633-650）；`<user_memory>` 信封在 `recallBlockSync`（:588-630）。
  - 任务：feed 会话每伙伴一个（`conversations.ts:275`，cid=`feed:<uid>:<agentId|default>`），与 CONTEXT.md「任务会话」词条「一个定时任务 = 一个专属持久会话」矛盾——代码注释（2026-09-07/09-30）是明确的实现记录。`tickInner` 逐用户逐任务 `await runTask` 串行（`tasks.ts:633-685`）；`taskRunner` followup + `whenIdle` + 末条 assistant 提取推送（`main.ts:196-209`）——同 feed 并发会让多任务同时醒来都取到末条回复，归属错乱。
  - 看护缺口：Turn Budget 封步数（app 装配 24）、流空闲超时、工具 timeoutMs、skill_exec 上限 600s（`skillexec.ts:15`）均已存在；无回合时长看护；`conversations.stop()` 走 abort 语义（保留部分输出、Inbox 清空）。
- 现状链路: 微信消息 → `handle()` 程序级过滤/聚合 → `runTurn`（ensureFeed → send/followup → whenIdle → slice(before) 提取 → 分段推送）；到点任务 → `Scheduler.tick`（30s）→ 串行 `taskRunner` → feed 会话回合 → 末条文本推送。
- 风险与不确定项:
  - steer 路由与媒体聚合/串行链的并发交错（timer flush 与轮询循环）需要保序测试覆盖。
  - 投影补全与 checkpoint 标注改变 wire 输出：存量会话下一个请求一次性前缀缓存失配（可接受，与日期锚上线同性质）。
  - 记忆行格式加 id 会触碰 app-memory 系测试的既有断言（需逐一适配）。
  - 分组并发后 tick 仍 await 全部组完成（ticking 防重入语义不变），慢组跨 tick 由 dispatch 时推 lastRun 防重发。

## 3. Innovate (Optional: Options & Decision)

### Option A（悬空修复位置：投影确定性推导）
- Pros: 日志 append-only 不破坏；合成结果紧随悬空 assistant 消息，wire 顺序天然合法；与日期锚同为铁律 2 认可的投影推导路径
- Cons: 每次投影多一遍配对扫描（全日志 id 集合，成本可忽略）

### Option B（悬空修复位置：装配时日志追加合成结果）
- Pros: 日志自洽，重放方无需感知推导规则
- Cons: append-only 只能追加到日志尾部，合成 tool/result 落在后续 user/message 之后，wire 顺序非法，反而制造新问题

### Decision（一）
- Selected: Option A
- Why: 位置正确性是硬约束，B 在 append-only 日志上无解。

### Option A（并发粒度：按 feed 会话分组，组内串行、组间并行）
- Pros: 完整保留现有「每任务推送取自己回合末条回复」的归属语义（同会话回合本就由 Inbox 排队串行）；改动只在 tickInner 分发层
- Cons: 同伙伴多任务仍串行（与会话模型一致，无法绕开）

### Option B（并发粒度：全并发 + 回合级事件归属推送）
- Pros: 同伙伴任务也并发（实际仍在同一会话排队，收益为零）
- Cons: 需重写 taskRunner 回复归属（按 turn 事件切片），改动面大且语义绕

### Decision（二）
- Selected: Option A
- Why: 并行收益全部来自跨会话，组内串行是会话模型的自然属性。

### Skip (for small/simple tasks)
- Skipped: false
- Reason: 两处存在真实分叉，其余设计（steer 路由条件、read_shadow 放 app 层、看护走 conversations + main 接线）无分叉，直接进 Plan。

## 1. Requirements (Context)
- **Goal**: 市面上的技能包（Anthropic 官方 skills 仓库、skills.sh 市场、带 Python/Node 脚本的第三方包、本地 ZIP）都能安装使用；安装与执行全程在 Docker 容器内，宿主机零污染；产物文件回到对话
- **In-Scope**:
  - 安装来源四类：ZIP 上传、直接归档 URL（`.zip`/`.tar.gz`）与单 SKILL.md URL、GitHub URL（仓库/`tree` 子目录/`blob .../SKILL.md` 三形态）、skills.sh URL
  - 包解析：根下必须有 SKILL.md；frontmatter 只取 `name`（≤64，字母数字连字符下划线，保留词禁用）与 `description`（≤1024），多余字段静默忽略；单文件/总量/文件数上限防 zip bomb
  - 安装流水线：起临时容器（基础镜像）→ 注入技能文件 → 安装智能体（固定配置 agent，shell/文件工具）读 SKILL.md 自行装依赖（Python 进 `.venv`、Node 进 `node_modules`、系统 CLI 走 apt）→ 确定性验证门（文件树比对、声明依赖实证装进 venv、脚本逐个 parse、运行前提 `command -v` 实证）→ 通过后 `docker commit` 技能镜像，`status=ready`；失败 `status=failed`，旧镜像继续服务
  - 执行：每次执行 `docker run --rm` 独立容器（从该技能镜像起），超时与 stdout/stderr/总输出上限，exit code 透传；产物写 `$SKILL_OUTPUT_DIR`（挂载本次运行目录）
  - 产物回传：执行工具结果含产物清单，模型筛选最终产物存 `conversation_blobs`，聊天显示附件卡片，微信链路外发
  - 渐进式加载三级：L1 目录层（`enabled && status==ready` 的绑定技能）常驻 system prompt；L2 `load_skill` 返回正文 + 捆绑文件树；L3 捆绑文件按需读取（新读取工具）
  - 绑定与可见性：沿用 per-agent `binding.skills`；技能记录扩展 `status`/`version`/`enabled`（停用只隐藏不删文件）；多用户按 uid 隔离安装，共用 docker daemon 与基础镜像
  - 前端：两步安装向导（来源 → 确认安装）+ 安装进度透明（安装智能体实时输出流、当前命令尾部、失败原因、重试、卡住时引导文字）+ 技能卡片（状态/版本/停用/文件浏览/卸载/「使用」按钮）+ 聊天输入框 `/` 弹已装技能自动补全，点选即填
  - 调用：自然对话触发（L1 目录）+ `/技能名` 命令（本回合注入强制指令：回答前必须先载入该技能正文，模型仍负责组织执行与解读）
- **Out-of-Scope**:
  - WeKnora 的目录/安装两层分离（单用户单 Docker 宿主无共享需求）
  - ClawHub、GitLab、SkillHub.cn 来源与 registry 协议探测（直链兜底）
  - 交互式终端、桌面沙箱、断线重连（无常驻会话需求）
  - 技能市场 / 跨用户共享 / 租户凭据四层解析
  - MCP 侧完善（另行立项，见调研报告第 7 节差距表另一半）
- **Acceptance Criteria**:
  - [ ] AC1 格式兼容：含多文件目录与脚本的市面技能包经 GitHub URL 与 ZIP 上传两条路都安装成功；frontmatter 含 when_to_use/license 等扩展字段不阻碍安装；单 SKILL.md 直链可装
  - [ ] AC2 安装流水线：依赖装进容器内 `.venv`/`node_modules`（宿主机无 pip/npm 落盘）；验证门四段全部执行且结果落安装日志；通过后存在该技能镜像且 `status=ready`；人为制造失败（缺声明依赖）时 `status=failed` 且旧版本镜像继续可用（升级场景）
  - [ ] AC3 执行隔离：脚本在 `--rm` 容器内执行，stdout/stderr/exit_code/超时回传模型；容器内无法访问宿主机 SQLite 数据与其他用户目录；并发执行互不干扰（含并发上限）
  - [ ] AC4 产物回传：脚本写 `$SKILL_OUTPUT_DIR` 的文件出现在执行结果清单中，模型可见产物元信息（名/大小/类型/ref），产物字节经 sha256 入 `conversation_blobs`；web 聊天在工具卡片下渲染附件列表并可经 `/api/skills/:sid/artifacts/:ref` 下载；微信端收到模型文字说明（微信链路无媒体外发能力，文件本体 web 端可达）
  - [ ] AC5 渐进式加载与铁律：L1 只含绑定且 ready 且 enabled 的技能；`load_skill` 返回正文 + 文件树；L3 文件按需读；所有模型可见内容可从会话日志重建（铁律 2，invariants 用例同步）
  - [ ] AC6 绑定与可见性：未绑定/停用/未就绪技能不出现在目录层与 `load_skill` 可用列表；`version` 变更可重装
  - [ ] AC7 前端：两步向导可完成安装（ZIP 与 URL 两路）；安装中可见智能体输出流与失败原因，可重试；`/` 触发自动补全并点选填入；卡片「使用」按钮跳会话预填命令
  - [ ] AC8 多用户隔离：用户 A 安装的技能对用户 B 不可见不可用；两用户各自安装同一技能互不影响
  - [ ] AC9 门禁：`pnpm test` 全绿（docker 交互全部经注入接口 mock，零网络零 docker，确定性测试）+ `pnpm typecheck` + `pnpm build:web`

## 2. Research Findings
- **事实与约束**:
  - 现状（`src/app/skills.ts` 150 行）：粘贴单文件全文 → SQLite `skills.body_md` 单字段；L1 目录层（`skillCatalogPrompt`）+ L2 `load_skill` 已实现且满足铁律 2；绑定走 agent `binding.skills`（id 列表）
  - harness 无任何子进程/docker 能力：`src/harness/env.ts` `PlatformEnv` 仅 fetch/now/randomUUID——容器交互必须作为新注入面扩展（铁律 1）
  - 服务器（118.145.107.158）：docker/python3 3.9.21/node 就绪；服务以 root 经 systemd 运行（宿主机直跑脚本 = root 风险，Docker 方案的核心理由）
  - OpenPrism 为多用户系统：`users` 表 + 注册页 + 全领域表 uid 隔离；微信桥已有媒体外发与 `conversation_blobs` 附件链路
  - WeKnora 机制结论（详见调研报告）：安装智能体读 SKILL.md 自行判断依赖是通用安装的唯一解（市面包无统一清单格式）；确定性检查后置为验证门；镜像快照 + 失败不切指针；frontmatter 只认 name/description 即可全兼容市面包
  - GitHub zipball 下载国内偶发超时——四类来源中直链兜底可绕开
- **现状链路**: 安装（粘贴）→ `skills` 表 → 目录层进 system prompt（每步 `listSync` 重取）→ `load_skill` 载正文 → 绑定经 `binding.skills` 在装配时生效（`conversations.ts:582-583,714`）
- **风险与不确定项**:
  - 安装智能体的 token 成本与分钟级耗时（透明进度 UI 已定案缓解体感）
  - docker 技能镜像数量增长（层去重缓解；卸载时删镜像）
  - 验证门的「实证 import」必须在容器内跑（宿主静态检查做不了）
  - 微信文件外发的大小/类型约束待查证（§2.1 Q6）
  - 基础镜像内 Python/Node 版本与国内 apt/pip 源加速待定（§2.1 Q1）

## 3. Innovate (Optional: Options & Decision)
> 七个分叉经 grilling 逐问定案（2026-10-21），完整问答见对话记录；此处记结论与理由。

### Decision 1 执行环境 → Docker 容器（弃宿主机受限执行）
- **Why**: 服务进程为 root，宿主机执行 = 脚本继承 root 可动 systemd 与 SQLite 本体；WeKnora 的验证门/Served 回退/快照语义建立在镜像可切换上，选 Docker 才能整套借鉴
### Decision 2 安装器 → 安装智能体 + 确定性验证门（弃纯确定性安装器）
- **Why**: 市面包无统一依赖清单（散文声明、系统 CLI），通用性只有会读文档的模型能覆盖；OpenPrism 自家 harness 起无头安装回合是现成能力
### Decision 3 绑定 → 逐 agent 绑定 + status/version/enabled（弃装了即全局、弃目录/安装两层分离）
- **Why**: `binding.skills` 现状零迁移；目录层 token 按需增长；单用户单宿主下两层分离无服务对象，Served 保护语义收进 status 字段
### Decision 4 Docker 分工 → 共用 daemon 与基础镜像；技能按 uid 归属；执行每起独立短命容器
- **Why**: 多用户隔离诉求在数据层与执行层已满足，无常驻沙箱需求（WeKnora 常驻因交互终端/桌面）
### Decision 5 前端安装界面 → 全流程透明（弃极简单步）
- **Why**: 安装是分钟级模型驱动过程，失败原因多样，无过程展示则无从诊断；引导框（SteerInstall 同款）在个人场景同样有用
### Decision 6 手动调用 → `/技能名` 命令 + 自动补全点选（must_use 语义；弃卡片直跑表单）
- **Why**: 手动诉求本质是强制使用而执行细节归模型；`/compact` 已建立命令心智；直跑表单打不服市面技能「参数语义写在散文里」的现实
### Decision 7 产物回传 → 模型经手的附件回传（`$SKILL_OUTPUT_DIR` + `conversation_blobs`；弃纯文本路径、弃全量自动回传）
- **Why**: 筛选「哪个文件值得给用户」是 SKILL.md 契约的一部分；附件/微信外发全是现成链路

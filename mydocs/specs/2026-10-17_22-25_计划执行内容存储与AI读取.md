## 1. Requirements (Context)
- **Goal**: 用户能把完整课表（组数×次数、发力要点、时间分配）存进计划本体，AI 问"今天练什么/怎么练"时能读出全文指导执行。
- **In-Scope**:
  1. 数据模型：plan 行加 `details TEXT`（≤8000 字），修订版本链自动携带。
  2. AI 写入：`create_plan` / `update_plan` 工具加 `details` 参数（update 不传=保持，传空串=清除）。
  3. AI 读取：`query_ledger what=plans/today` 条目带 `hasDetails` 标记（摘要不膨胀）；新增 `what=plan&planId` 单查返回 details 全文；persona 计划规则加一句引导（有详情可单查）。
  4. Web 写入：`POST /api/plans`、`PUT /api/plans/:id` 收 `details`；今天页计划编辑框加详情 textarea。
  5. Web 展示：计划行有详情时可展开查看全文。
- **Out-of-Scope**:
  - 结构化课表建模（动作/组数/休息分列）——details 是自由文本，不做 schema 化（用户内容形态多样，文本最通用）。
  - 定时任务自动带出 details（简报模型经 query_ledger 自主单查，不强制注入）。
  - 旧计划批量补录（用户对存量 5 个习惯计划自己补内容）。
- **Acceptance Criteria**:
  - [ ] AC1: create_plan 带 details 落库；query_ledger what=plan 返回全文；what=plans 列表该条带「有详情」标记且不渲染全文
  - [ ] AC2: update_plan 改 details = 追加新版本行（planId 不变、历史打卡引用不断）；空串清除；不传保持
  - [ ] AC3: 用户对话「今天练什么」链路可用：模型 today 看到计划+有详情 → 单查拿全文 → 能复述具体组数×次数（工具级测试模拟此链路）
  - [ ] AC4: /api/plans POST/PUT 收 details；PUT 走 mergePlanUpdate 白名单同源校验
  - [ ] AC5: 今天页：计划行展开显示详情全文；编辑框可改可清空
  - [ ] AC6: pnpm test 全绿 + typecheck + build:web
  - [ ] AC7: 部署后用户真机给 5 个训练计划补上详情并验收 AI 能指导

## 2. Research Findings
- 事实与约束:
  - `PlanRecord`（ledger.ts:34-43）仅 title/scope/due/ndays/timesPerPeriod/goalId——无内容字段；`ledger_entries` 表有 note/attrs_json 列但 plan 行未用。
  - AI 读计划唯一路径 = `query_ledger`（tools.ts renderQuery）：today 出「今日必做/未完成计划」摘要（标题+planId+进度+打卡 seq），plans 出列表（标题+planId+习惯配额+due）——**全文直接塞摘要会爆**（5 计划×2KB=10KB/次）。
  - 写入三入口已并存：工具 create_plan/update_plan（mergePlanUpdate 校验合并，与 UI 同源）、POST/PUT /api/plans、前端 PlanRow 编辑（title/due）。
  - 前端 Today.tsx PlanRow：编辑对话框 title+due（deadline 型）两字段；无新建表单的 details 入口（新建在 /api/plans POST 对应的表单，同样要加）。
  - 折叠层（fold.ts）todayView 按 plan 最新版本行渲染——details 加列后 rowToRecord 带出即可，状态机零感知。
- 现状链路: 用户口述课表 → AI 建 5 个周习惯计划（只存标题）→ 用户问怎么练 → 模型 query_ledger 只有标题 → "系统里存不进去"（属实）。
- 风险与不确定项:
  - details 长文本进入 query_ledger plans 全文渲染的风险 → 以 hasDetails 标记 + 单查分支规避。
  - 前端新建计划表单位置待实现时确认（Today.tsx 新建入口）。

## 3. Innovate (Optional: Options & Decision)
### Option A: details 专列（ledger_entries 加列）
- Pros: 类型一等公民（PlanRecord.details），读写路径直观，UI/AI 消费无歧义；ensureColumn 幂等加列是项目常规操作。
- Cons: 动 DDL + INSERT/SELECT 列清单（三处小改）。
### Option B: 复用 attrs_json（attrs.details）
- Pros: 零 schema 改动。
- Cons: attrs 值类型 Record<string, string|number> 语义是"自由属性"，计划的执行内容是核心载荷不是附属属性；类型不直观。
### Decision
- Selected: Option A（details 专列）。
- Why: 执行内容是用户核心诉求的本体（AI 要常读常引用），值得一等字段；ledger 哲学"结构定死"——计划内容属于结构语义；改动面仅底座三处。

## 7. Plan-Execution Diff
- 单查返回 `{ planId, title, scope, state, details… }` → 实现无 `state`（§4.2 偏差，评审 m7）：state 是折叠层对今天的视图语义（overdue/doing…），单查的对象是计划本体，模型执行指导用不到——不搬。返回包一层 `{ plan: {...} }` 键与 render 的 plans/flows/date 形态判别对齐。
- update_plan 回执追加「（已存执行内容）/（已清除执行内容）」确认 + create_plan 回执「（已存执行内容）」（评审 m3：模型看不到原始载荷，回执不渲染就等于不存在）。
- create_plan 的 details 空白串=不落键（≠update 的清除语义）——创建时没有旧值可清，空白即未提供。
- todayView 加 options.includePlanDetails 区分 HTTP 面（带全文）与模型面（只标记）——超出原 Plan 的实现细节，双面口径是本功能最关键防线。

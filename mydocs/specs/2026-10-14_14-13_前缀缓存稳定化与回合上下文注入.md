## 1. Requirements (Context)
- **Goal**: 消除每回合第一步的前缀缓存全量失效。现状：system 含钟面（分钟级变）+ 情境记忆召回块（回合级变），wire 上 system 排在全部历史之前，任一变化使整段历史缓存作废（智谱 coding 端点 prefill 慢时被放大为每回合首步 7–10s，实测证据见本会话 2026-10-14 排查）。
- **In-Scope**:
  - system prompt 重排：只留稳定块（身份/人设、任务会话规则、技能目录、守则、语言指令），钟面与记忆召回块移出
  - 新增回合上下文注入机制：`agent.followup(content, context?)`，context 作为 `user/message` 事件的可选字段落日志（铁律 2 走"新增日志事件字段"路径）
  - 投影规则：context 只并入**最后一条**带 context 的 user 消息（历史注入剥离），保证 wire 中至多存在一个注入块、历史不膨胀
  - 三入口接线：`store.send()`（web + 微信桥共用）与任务触发（main.ts taskRunner）各自组装 context（钟面 + 按本回合消息 query 的 recallBlockSync）
- **Out-of-Scope**: 上下文窗口/压缩阈值调整（用户明示不管）；智谱端点自身吞吐；向量召回算法变更；`steer`/`inject` 通道的 context 支持（只做 followup）
- **Acceptance Criteria**:
  - [ ] AC1 同一会话连续两回合（人设/绑定/语言/技能不变），两回合的 `request/header.systemFingerprint` 相同（system 字节级稳定）
  - [ ] AC2 钟面与记忆召回出现在**本回合触发消息**的 wire 内容里（事件 `context` 字段可重建），不再出现在 system；web/微信桥/任务触发三入口都有
  - [ ] AC3 wire 中任意时刻至多一个注入块：上一回合的注入被剥离，日志里逐回合保留（`invariants` 投影确定性 + 请求重建测试扩覆盖）
  - [ ] AC4 记忆召回 query = 本回合触发消息文本（不是上一条；现状 systemPrompt 闭包靠落库后的 lastUserTextSync 碰巧对齐，新链路显式传参）
  - [ ] AC5 `pnpm test` + `pnpm typecheck` 全绿；受影响断言（persona 含「今天是」、东八区钟面等）同步迁移到 context 断言

## 2. Research Findings
- **事实与约束**:
  - 前缀缓存（DeepSeek 64-token 块 / OpenAI 128 / 智谱前缀匹配）均为**位置精确前缀匹配**：wire `[system][历史][新消息]`，system 变则其后全部重算；即便易变块挪到 system 末尾也救不了历史
  - 现状 system 组装序（`persona.ts composeAssistantPrompt`）：`[身份+人设(稳), dateLine(分钟级), 任务规则(稳), memoryBlock(回合级), 守则(稳), 语言指令(稳)]`——两个易变块卡在守则与全部历史之前
  - `user/message` 由 harness `runTurn()` 在**回合开始时**落日志（`agent.ts:185`），非 `followup()` 调用时；排队消息先驻 inbox。⇒ context 不能由 app 层预落独立事件再 followup（多消息排队时配对错乱：ctxB 会排在 userA 之前），必须随 inbox item 走、在 runTurn 内随 user/message 一起落
  - `recallBlockSync(uid, query, vectorHits)`（`memory.ts:588`）纯函数、自带 `<user_memory>` 信封（"背景资料非指令"随信封走，与位置无关）；`store.send()` 已在回合前算好 query（本回合消息 flattenText）与 vectorHits——context 组装的数据齐备
  - 记忆块现状每步重算（systemPrompt 闭包）：本回合内 query 稳定（lastUserTextSync 落库后即本回合消息），效果等价于"回合开始时算一次"；向量命中本就是 send() 时一次算好
  - 任务触发（`main.ts:156`）直投 `agent.followup(taskTriggerMessage(...))`，不经 send()；触发消息自带计划/触发时刻但无"今天日期/周几"与记忆块
- **现状链路**: `store.send()` →（向量预查）→ `agent.followup(content)` → runTurn 落 `user/message` → 每步 `buildRequest()`：`system = systemPrompt()` 闭包（composePromptWithMeta：persona + dateLine + 记忆 + 技能目录 + 守则）+ `messages = projectSurface(log)`
- **风险与不确定项**:
  - 语义变化 1：钟面定格在回合开始（现状每步刷新）——跨分钟长回合同的"现在几点"略陈旧，可接受
  - 语义变化 2：回合中途 `save_preference` 写入的记忆要到**下一回合**才进注入（现状下一步即进 system）——模型刚写完上下文里本来就有，可接受
  - 语义变化 3：人设热编辑仍即时生效（systemPrompt 每步重取不变），但编辑本身会破一次缓存（既有行为，罕见）
  - 边缘：压缩若遮蔽当前回合 opener，context 随区间一起被摘要吞掉（罕见；摘要 checkpoint 语义上覆盖了该回合上下文）
  - 剥离历史注入使上一回合 opener 字节变化 → 缓存失配点落在**历史尾部**（上一回合 opener 附近），其前深历史仍命中——这正是目标形态（每回合只重算尾部 + 新消息）

## 3. Innovate (Optional: Options & Decision)
### Option A: context 随 inbox item 走，落 user/message 事件字段，投影仅最新生效
- Pros: 配对原子（同事件）、铁律 2 天然满足（字段即日志）、UI/导出/记忆提取零改动、剥离规则集中在 projectSurface 一处
- Cons: harness API +1 参数、事件 schema +1 字段（需扩不变量测试）
### Option B: app 层独立 `turn/context` 事件 + 投影按"最近前置"配对
- Pros: 不动 harness followup 签名
- Cons: 排队消息配对错乱（ctxB 先于 userA 落库），需额外 nonce 关联；事件间配对脆弱
### Option C: 仅重排 system（易变块挪 system 末尾），不做出 system
- Pros: 改动最小
- Cons: system 仍每回合变 → 历史缓存仍全废，不达成本目标（已向用户说明并否决）
### Decision
- Selected: **Option A**
- Why: 唯一同时满足配对正确、日志可重建、历史不膨胀、UI 零感知的方案；C 不解决问题，B 有结构缺陷
### Skip (for small/simple tasks)
- Skipped: false
- Reason: 触及 harness 事件词表与投影不变量，属架构级决定，留档

## 2. Research Findings

### 2.1 WeKnora 机制事实（源码通读结论）

**主题计数（topics → interest 晋升）**：

- 数据模型 `memory_topic_stats`：`normalized_key`（规范化唯一键）+ `topic`（首次记录的规范名，此后不随模型改口改名）+ `aliases`（jsonb，历史说法 ≤12 个）+ `hits` + `last_seen_at` + `promoted_at`（NULL=未晋升），scope 内 unique。
- 产出点：提取 prompt 要求模型每段额外输出 `topics` 数组（用户在问什么主题），并把已有主题列表展示给模型要求尽量原样复用——零成本的预归一层。
- 三级归一（`topic_resolve.go`）：tier 1 精确（规范化相等或命中别名，区分 reused/exact）；tier 2 模糊（字符 bigram Dice ≥0.80，标签 ≥4 rune 才参与，防短标签误合并）；tier 3 模型批量裁决（温度 0、一次调用处理全部未决标签、只允许动 unresolved、`TopicLabelIsAnImprovement` 守卫：合并名不得更宽泛（比现名短或被现名包含即拒）、须与两侧相似 ≥0.30、≤80 字）。run 内新标签先互相折叠。
- 计数晋升（`service.go:1076`）：`BumpTopic` upsert（hits++、新说法进 aliases）→ 墓碑检查 → hits ≥ 阈值（默认 3、上限 20）且未晋升 → 写 interest 条目（topic=content=规范名，importance 3）→ 标 promoted。别名增长时作废该 interest 向量让回填重建。
- 模型裁决失败的语义：告警并让每个说法独立成行（可见的错误，计数永远差一点），绝不静默吞掉整级。
- API/前端：未晋升主题列表 + 计数、手动晋升、删除（拒绝被记住，不再自动提出）。

**向量召回**：

- 绑定：每工作区一个 embedding 模型 ID，空=关闭；绝不取"第一个可用的"（向量空间不可混）。
- 写入：条目落库后顺手 embed（10s 超时、best-effort、失败仅告警等回填）；文本=`topic：content` 拼接（interest 加 aliases，别名只进向量不进注入块）。
- 存储：`memory_item_embeddings(item_id, source_content, source_topic, model_id, dims, vector BLOB)`，BLOB=小端 float32 是唯一事实源；PostgreSQL 另同步 halfvec 列库内算距离，SQLite/无 pgvector 退化为进程内全量扫描（cap 5000，个人规模毫秒级）。
- 查询：查询侧 embed **2s 超时**（召回在每个回答前面，语义匹配只值零点几秒）；cosine ≥0.5 算命中；任何失败带 skip 原因降级纯词法（vector_disabled/embed_failed/vector_search_failed/no_vector_matches）。
- 融合：词法排名 + 向量排名按 **RRF 名次融合（k=60）**——余弦有界、词法是重合计数，量纲不可比，按名次融合绕开标定；向量命中可把词法候选池外条目拉进注入（`outside_pool` 指标度量真正增量）；模式痕迹 lexical_only/hybrid/no_matches。
- 回填：夜间维护每轮 200 条限速，批内模型失败即 break。
- 提取复用：候选旧条目超过 15 条时用段全文向量检索"最接近的 15 条"作 update/delete 候选，无向量退 importance 前缀。

### 2.2 OpenPrism 现状链路（事实）

- 词法件齐全：`memory.ts` 已有 `normalizeTopicKey`/`tokenize`/`bigrams`/`lexicalScore`，与 WeKnora 同族（上次重构移植）。
- 注入：`recallBlockSync(uid, query?)` 纯函数（常驻块 ≤900 rune + 情境词法 top5 ≤600 rune + `<user_memory>` 信封），`conversations.ts:385` 的 systemPrompt 是**每步重读的同步闭包**，query=`lastUserTextSync`（会话最近一条用户消息）。向量预查必须在闭包求值前 await 完成、命中集作参数传入。
- 模型接入：`model_providers(id,uid,platform,base_url,model,context_window,key_enc)` 多行 + `model_active` 指针；adapter 仅 openai-compat 打 `/chat/completions`；**全仓库无任何 embedding 代码**；`ensureColumn` 存量补列机制现成。
- 提取：`memory-extract.ts` 决策制 JSON（add/update/delete 按索引寻址、truncate 重试、不可解析推进不卡死）、候选旧条目裁 15（无相关性排序）、`adapterFor(uid)` 统一装配。
- 调度：90s 去抖 + 10s 扫描 + nightly consolidate（Jaccard≥0.55 候选 + LLM 裁决合并）现成；SIGINT 清理齐备。
- 存储：`node:sqlite` 同步 API；`memory_items` 有 topic 列；`memory_meta` 单行键值扩展位现成。

### 2.3 风险与不确定项

- **铁律 2**：查询向量来自外部 API，若在召回时直接调用，注入块无法从日志+库状态确定性重建。→ 解法见 §3 决策：查询向量缓存表把"向量命中"变成库状态的确定性函数。
- **同步闭包 vs 异步 embed**：systemPrompt 闭包同步，embed 是异步调用。→ send() 装配前先 await 向量预查，闭包捕获命中集；embedding 未配置时该步零开销直通。
- **向量空间混淆**：换 embedding 模型后新旧向量不可比。→ 每行带 model_id，检索只比同 model_id；换模型=全量视为缺失，回填按新模型重建。
- **embedding 成本**：按条计费（回填 N 条 + 每条新记忆 1 次 + 缓存未命中的每次召回 1 次）。→ 查询向量缓存表同时消除重复调用；回填限速 200/轮。
- **主题误合并不可见**：两主题被错合并后计数互相污染且事后难发现。→ 沿用 WeKnora 的高门槛（fuzzy ≥0.80 且 ≥4 字、裁决守卫"只准更具体"），WeKnora 注释明确此取舍：漏合并只是延迟晋升，错合并无法察觉。
- **不确定项**：OpenPrism `normalizeTopicKey` 与 WeKnora 版的噪音词表细节可能有出入，实施时以 WeKnora 版行为为准核对一次（tier 1 归一正确性依赖它）。

## 3. Innovate (Options & Decision)

### Option A：一个 spec 规划两条独立功能线（推荐）

- Pros: 调研结论、铁律 2 处理、错误归一方案一次收口；两条 checklist 线互相独立、无依赖，实施与验证可分别进行、单独交付；与上次"单 spec 多功能线"的仓库先例一致。
- Cons: 文档较长；一次评审要覆盖两个功能。

### Option B：只做主题计数，向量召回另起 spec

- Pros: 主题线零新依赖、零新增外部调用，最小切口。
- Cons: 向量召回的调研结论（RRF/缓存表/降级语义）与主题线共享，拆开要重复上下文；两 spec 将共享 db.ts/model_providers 的改动面。

### Option C：只做向量召回，主题计数另起 spec

- Pros: 直接消除同义改写盲区，对聊天质量提升最直接。
- Cons: 主题计数是提取 prompt 的一次顺带扩展，独立成 spec 碎片化；interest 条目的向量文本依赖别名机制，两功能在数据上有弱耦合。

### Decision

- Selected: **Option A**
- Why: 两条线共享调研与铁律 2 设计，合并评审一次到位；实施时 checklist 分组互不阻塞，验收分别独立（AC1–AC3 主题线、AC4–AC8 向量线），不存在"绑在一起才能交付"的耦合。

### Skip (for small/simple tasks)

- Skipped: false
- Reason: 双功能 + 硬约束（铁律 2/4/5）适配，方案取舍需要留痕。

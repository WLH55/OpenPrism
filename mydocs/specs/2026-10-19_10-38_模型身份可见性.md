## 1. Requirements (Context)
- **Goal**: 用户在会话里问「你是什么模型」时，AI 如实回答当前生效模型的平台与型号；界面上可核对每条回复的实际生成模型
- **In-Scope**:
  - 回合上下文注入当前生效模型信息（web `send()`、微信桥、任务触发三入口同口径）
  - 前端聊天页逐回合模型标记（基于 `request/header` 事件）
- **Out-of-Scope**:
  - 手动压缩入口（用户问题 2 延伸，如需另行立项）
  - 模型计费/用量统计
  - 回合内逐 step 区分模型（同一回合内多步共用同一 adapter，无区分意义）
- **Acceptance Criteria**:
  - [ ] AC1 会话内问「你是什么模型」，AI 回答的平台与型号和模型配置一致（真机验收留用户；测试断言注入内容本身）
  - [ ] AC2 切换会话绑定模型后，下一回合注入新模型（与 adapter 每回合现读同口径）
  - [ ] AC3 微信桥与任务触发入口同样注入正确模型
  - [ ] AC4（若选 B）聊天页历史消息可见逐回合模型标记，向上翻页加载后标记保持
  - [ ] AC5 注入内容随 user/message 事件 `context` 字段落日志（铁律 2）；wire 至多一个注入块不变（invariants 用例同步）

## 2. Research Findings
- **事实与约束**（2026-10-19，main @ af46113）:
  - 界面现状：聊天页头部已有当前生效模型标签与切换入口——`web/src/pages/Chat.tsx:466-476`（前端三级链 `boundProvider ?? agentDefaultProvider ?? globalProvider` 计算 `effectiveProvider`，`modelShortLabel = platform · model`）、`Chat.tsx:498-507`（徽标「本会话/伙伴默认/全局」+ 模型切换下拉）、`Chat.tsx:609-614`（窄屏面板同款）；宽屏 `hidden md:flex` 可见。
  - AI 不自知的根因：system prompt 只含稳定块（人设/身份/技能目录/任务规则/守则/语言，`src/app/conversations.ts:650-659`），回合上下文只含钟面 + 记忆召回（`conversations.ts:635-643`）——两处均不含模型信息，模型对自身身份的感知只来自训练数据，不可靠。
  - 生效模型三级链（服务端权威）：`conversations.ts:509-513` `effectiveProviderId`（会话绑定 `conversations.model_provider_id` → 伙伴默认 `agents.model_provider_id` → 全局 `model_active`）；adapter 每回合现读该行（`src/app/main.ts:68-82` `modelConfigFor` / `adapterFactory.complete` 内 `readModelProviderConfig` 现读）。
  - `ModelConfig` 携带注入所需字段：`src/app/secretbox.ts:44-56`（`platform` 显示名保存时由 baseURL 推导落库 `secretbox.ts:71-98`；`model` 型号字符串）。
  - 注入通道现成：`Agent.followup(content, context)` 携带 → user/message 事件 `context` 字段落日志（铁律 2 天然满足）→ 投影只给最后一条带 context 的用户消息前插〔系统上下文〕块（`src/harness/session/project.ts:79-89, 138-146`），wire 至多一个注入块、system 与深历史前缀缓存不受影响。
  - 三入口：web / 微信桥走 `send()`（`conversations.ts:691` followup 注入）；任务触发走 `taskFeedContext`（`conversations.ts:645-648`，main.ts 任务直投 followup）。
  - 逐回合标记原料已存在：`request/header` 事件（provider + model + 指纹，`src/harness/session/events.ts:75-81`；指纹变化才落一条，`src/harness/core/agent.ts:120-137`）已持久化进 conversation_events 并随 events 接口返回，但前端 `foldEvents`（`Chat.tsx:23-70`）将其丢弃。事件里 provider 是写死标签 `"byok"`（`conversations.ts:611-614`），可用字段只有 model 字符串。
  - `send()` 内已有 `modelConfigFor` 调用先例（图片多模态校验 `conversations.ts:675-679`，仅带图时读取）；`turnContextFor` 是同步函数，模型行需由 async 调用方取好传入。
- **现状链路**: 生效模型三级链每回合现读 → adapter 现读同一行 → 注入行若同源现读，则与实际请求模型天然一致（中途改绑定时二者读到相同最新值）。
- **风险与不确定项**:
  - 前缀缓存：context 走回合级注入块（user 消息内容前插），system 不动，与 2026-10-14 设计同路，无新增失配点。
  - 压缩吞注入：复用既有边缘口径（摘要 checkpoint 语义覆盖该回合上下文），无新增风险。
  - `request/header` 无 platform 字段：前端标记显示 model 字符串即可（无歧义）；按 model 精确匹配 providers 反查 platform 存在多行同 model 的歧义，不做。
  - 每回合多一次 `readModelProviderConfig`：SQLite 单行主键查询，与 adapter `complete` 内现读同量级。

## 3. Innovate (Optional: Options & Decision)
### Option A 回合上下文注入「当前底座」行
- 内容: `send()` / `taskFeedContext` 取 effectiveProvider 的 `ModelConfig`，在回合 context 顶部加一行「当前底座：{platform} · {model}」；AI 被问模型身份时据此如实回答
- Pros: 直击用户场景（问 AI 答不上来）；三入口同口径；铁律 2 天然满足（context 落日志）；不碰 system 前缀缓存
- Cons: 每回合注入块多一行（个位数 token）
### Option B 前端逐回合模型标记
- 内容: `foldEvents` 消费 `request/header` 事件的 model 字符串，聊天页在对应回合的 assistant 消息上显示小徽标
- Pros: 事后核对每条回复的实际生成模型（历史会话中途切过模型的场景尤其有用）；纯前端改动
- Cons: 只显示 model 字符串（无 platform）；header 指纹变化才落，需按区间映射（Q3）
### Decision
- Selected: A+B（推荐值记录；用户 AskUserQuestion 未即时作答，若另有所选按 §8 改向）
- Why: 两者互补不互斥——A 解决「问 AI 答不上来」，B 解决「事后核对每条回复」；均复用现成机制（注入通道 / request/header 事件），改动面小

- Skipped: false
- Reason: 存在两个互补方向，需用户决策范围

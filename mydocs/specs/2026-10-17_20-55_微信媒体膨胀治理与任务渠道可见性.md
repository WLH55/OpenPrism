## 1. Requirements (Context)
- **Goal**: 消除微信图片导致的会话日志膨胀与全站卡顿；让 agent 能看到定时任务的通知渠道。
- **In-Scope**:
  1. 图片落库分离：base64 数据搬出 `conversation_events.event_json`，入独立 blobs 表，事件里留引用。
  2. 存量迁移：生产库 29MB 一次性搬迁（幂等，可重跑）。
  3. LLM 投影按**回合窗口**保留图片：仅最近 R=2 个回合内的图片进模型上下文（同回合多张全保留），更早的替换文本占位——老图不常驻，自然滚出。
  4. 前端聊天图片按 blob 引用懒加载（接口取图），兼容迁移前的内联形态。
  5. `query_tasks` render 渲染通知渠道与启停态。
  6. 微信入站媒体聚合窗口：连发多图（iLink 一图一消息）在短窗口内合并为一个回合发给 AI；窗口内来文本则文本+图立即同发；语音转写算文本。
- **Out-of-Scope**:
  - 智谱 coding 端点 prefill 慢（上游问题，前缀缓存稳定化已做，另测）。
  - 20:00 晚间汇报微信推送 `ret=-1 invalid request`（iLink 侧，未定位，另开任务）。
  - 压缩触发口径调整（图片 1024 token/张是 vision 模型正确口径，不动）。

## 2. Research Findings
- 事实与约束（生产实测 2026-10-17 20:4x）:
  - 系统资源无瓶颈：load 0.01、内存可用 1.8G、进程 262MB、`/api/health` 本机 1.5ms。
  - 巨会话 `wechat:59348383…`：1153 事件 / event_json 共 29MB；`user/message` 139 条平均 201KB（最大 1MB）；**今天一天 +26.78MB**。
  - 膨胀源=消息 `message` 字段里的 image block base64（`text` 空、`context` 仅 1KB）：`src/app/wechat-bridge.ts:350` `plain.toString("base64")` 直接入块。
  - 前端已分页（`web/src/pages/Chat.tsx:157` limit=50），但单页内大图事件仍可几十 MB → 对话记录加载不出。
  - send 投影全量：`readEvents` 无参全量（46ms 同步查询）+ `JSON.parse` 29MB（主线程数百 ms，阻塞事件循环 → 全站卡）；`projectSurface` 对 image block 零裁剪（裁剪只对 tool_result 文本）→ **历史全部图片 base64 进每个 LLM 请求**。
  - 压缩从不触发：`meter.ts:17` 图片固定 1024 token/张（vision 口径，正确），压力远低于阈值——字节负担被 token 口径合理低估，膨胀无闸。
  - 任务渠道 bug：`query_tasks` execute 返回 `notifyChannel`（tasks.ts:801）但 render 只输出「标题（内置）」（tasks.ts:774-778）；`pipeline.ts:133` 证实 render 输出=模型所见。
  - 生产任务数据真相：用户 59348383 的每日简报 `channel=wechat, enabled=1, 08:30` —— **用户设置没丢，agent 看不见**。
- 现状链路:
  - 写：微信图片 → wechat-bridge 下载解密 → base64 image block → `user/message` 事件全量落库。
  - 读：GET /events（分页但单页可能巨）→ 前端渲染；send → readEvents 全量 → projectSurface → LlmRequest（图片全带）。
- 风险与不确定项:
  - 迁移重写存量 `event_json`：只改内容不改 seq/type/ts（UPDATE），投影/不变量不受扰动；需幂等（内联 data 存在才处理）。
  - 部署窗口新旧形态混存：前端必须同时渲染内联 data 与 blobIdx 引用两种 image block。
  - 铁律 2 口径扩展：「日志」= 事件表 + blobs 表联合（可重放性不变），invariants 需同步。

## 3. Innovate (Optional: Options & Decision)
### Option A: 图片存储分离 + 投影预算（治本）
- Pros: 事件日志回归轻量（读/投影/接口全链路瘦身，一劳永逸）；前端按需拉图天然懒加载；blobs 表仍是日志的一部分，铁律 2 合规；迁移一次解决存量 29MB。
- Cons: 改动面大（写/读/投影/前端/迁移/不变量六处）。
### Option B: 纯读路径裁剪（不动存储）
- Pros: 改动小，只裁投影与接口输出。
- Cons: 29MB 仍在库内，每次 readEvents/JSON.parse 依旧阻塞事件循环；前端显示旧图仍需大响应；不治本。
### Decision
- Selected: Option A；B 的「投影图片预算」并入 A 作为组成件。
- Why: 用户的卡顿是全链路的（读接口/投影/LLM 请求三者都吃 29MB），只有存储分离能同时解决；且铁律 2 的可重放语义在新形态下依然成立。

## 7. Plan-Execution Diff
- **blobs 主键 (cid, seq, idx) → sha256 内容寻址 ref**（§4.1/§4.2 偏差）：实现改为 `conversation_blobs(ref TEXT pk, media_type, data BLOB)`——同图跨消息/跨会话天然去重，块自包含（无需 cid/seq 反查）；路由随之 `/blobs/:ref`。取舍：删会话不回收 blobs（无反向引用，泄漏 MB 级/图，后续可加 GC），代码注释与 DDL 已留痕。

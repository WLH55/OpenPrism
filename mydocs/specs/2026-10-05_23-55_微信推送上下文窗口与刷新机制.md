- **In-Scope**:
  - A：推送失败可见化（失败原因分类 + 12h 去重的站内提醒）
  - A：IM 通道页上下文窗口健康度（上次消息时间 + 四态）
  - A4：agent 侧可见化——create_task/update_task 设 wechat 渠道时，工具执行结果回报绑定真实状态
  - C：内置简报/汇报默认文案追加保活引导句（经 ensureBuiltins 单源同步覆盖存量）
- **Out-of-Scope**:
  - B：推送成败落库实测（本轮缓，后续单独做；Q1 保持开放）
  - 更换/新增通知基建（Web Push、邮件、短信）
  - iLink 协议逆向新接口（只使用已实证的 getupdates/sendmessage）
- **Acceptance Criteria**:
  - [ ] AC1: 微信推送失败时收到站内提醒（12h 内去重），原因可区分：上下文过期（「回句话即恢复」）/ 绑定失效（「重新扫码」）/ 其他错误（附原因简述）；未绑定（unbound）保持静默
  - [ ] AC2: IM 通道页绑定卡显示推送通道健康度：上次消息时间 + 四态（未对话 / 新鲜 <11h / 将过期 11–13h / 已过期 >13h），阈值常量注明 12–14h 社区口径

## 2. Research Findings
- **事实与约束**:
  - context_token 是 iLink 给每条「用户→机器人」消息附带的**会话上下文令牌**：机器人发消息必须挂在它上面，iLink 用它判定对话是否「活着」（本质类似公众号客服消息的回复窗口凭据，但窗口短得多）
  - token **可复用**（非一次性），但**会过期**：社区逆向实测约 **12–14 小时**（wechat-world-claw）；自家实证上界——最后用户消息 10-02 08:00，10-05 20:00 推送 `ret=-2 prepare failed`（3.5 天必失效）
  - **唯一刷新途径 = 用户发来新消息**（getUpdates 每条入站消息带新 token，我们已存最新一条到 wechat_binds.last_context_token）；**机器人发送不刷新窗口**（社区一致结论 + 事实反推：若发送可续期，9-30 起每日两次成功推送不会断）；无公开 refresh/keepalive API
  - iLink 无官方文档（WeKnora 注释同源确认），策略可能随微信侧调整；错误形态有两类：`errcode -14`（bot_token 失效→重新扫码）与 `ret=-2 prepare failed`（context 过期→用户发消息激活）
- **现状链路**: 任务到点 → notify（channel=wechat）→ `wechat-bridge.pushText(botToken, ilinkUserId, last_context_token)` → 失败 `console.error` 一行（journal 还会被刷掉）→ 静默退站内；用户全程无感知。IM 通道页只显示绑定状态（active），不显示上下文新鲜度
- **「程序模仿用户消息刷 token」不可行的机制分析**（2026-10-05 追加，用户提问）:
  1. token 是**微信服务端签发并维护的会话状态**，只随真实用户消息（getupdates）签发；本地伪造/复用旧 token 只改我们库里的字符串，改变不了服务端的窗口计时——`prepare failed` 校验的是微信侧会话，不是 token 字符串本身
  2. 「以用户身份发消息」= 自动化一个真实微信号走客户端协议：违反微信使用条款（封号风险），且该会话的另一端就是用户本人的微信——等于要自动化用户自己的账号，安全与工程都不成立
  3. **生产实证（最有说服力）**：9-30 起 bot 每天两次成功推送（简报 8:30 / 汇报 20:00），10-02 08:00 用户停止说话后窗口照样过期——机器人侧流量不计入窗口。这一周的生产数据本身就是「bot 发送不续期」的反证实验，Q2 就此关闭
- **风险与不确定项**: 12–14h 是社区数字，未用自家数据校准；journald 只保留 <1 小时，排障历史易丢失

## 3. Innovate (Optional: Options & Decision)
### Option A: 失败可见化 + 上下文健康度（纯体验层）
推送失败时站内兜底文本带恢复指引（区分 -14 / prepare failed）；IM 通道页显示「上次消息 HH:mm + 窗口状态（新鲜 <11h / 临近过期 11–13h / 已过期 >13h）」
- Pros: 改动小（bridge + notify 文案 + IM 页一块卡片）；立刻消除「无感知断流」；不依赖未实证假设
- Cons: 不延长窗口本身——用户不说话仍会断（但断得明白、恢复得快）

### Option B: 推送成败落库 + TTL 实测（数据层）
wechat_binds 加推送结果字段（或轻量 push_log 表）：每次 pushText 记录 ts/结果/错误码；健康度与提示文案以它为准
- Pros: 回答 Q1/Q2 的唯一途径；为未来保活策略供数；也是 A 的数据底座
- Cons: 需迁移/DDL；记录本身不解决断流

### Option C: 产品化「保活」引导（对话层）
利用「用户回一句 = 刷新窗口」：简报/汇报结尾加一句引导（如「回个“好”就行，也让我知道你在线」）；可选：检测到当天用户 0 消息且 20:00 前窗口将过期时，简报语气加强提醒
- Pros: 零协议风险；把刷新动作变成自然交互；配合 A 后用户知道为什么要回
- Cons: 依赖用户行为，非保证；文案侵入感需要拿捏

### Option D: 机器人侧自动刷新（协议层）
结论：**不可行**——token 只能由用户消息刷新，无公开 keepalive API，「发送续期」假说被生产数据反证否定（见 §2）。列入选项仅为存档，防止后续重提。

### Option E: 程序模仿用户给机器人发消息（用户 2026-10-05 提问）
结论：**不可行**——token 是微信服务端会话状态，本地伪造无效；「以用户身份发送」需自动化真实微信号（违反条款 + 需自动化用户本人账号）。详见 §2 机制分析。存档防重提。

### Decision
- Selected: **A + C**（2026-10-06 用户选定；B 本轮缓——避免 DDL，健康度先按 last_msg_ts 时间推算，精确窗口实测留给 B 后续单独做）
- Why: A 解决「断流无感知」的直接痛点且改动小；C 把唯一可行的刷新动作（用户回话）产品化；D/E 已证不可行
### Skip (for small/simple tasks)
- Skipped: false
- Reason: 涉及服务端错误分类、通知文案、内置模板、前端页面四处联动，非小任务

## 2. Research Findings

### 2.1 OpenPrism 现状（事实）

- **三层结构**：L1 指纹镜像（chat/ledger/tasks 三 surface，sha1 短指纹 diff → l1_changes）→ L2 条目事实（l2_entries：id/section/text/refs，section 白名单就近落档，`ref#fingerprint` 门控防停滞）→ L3 槽文档（memory_slots 四槽 markdown，只吃新 L2 entry，脚注=surface 名，preferences 永不自动综合）。
- **触发**：`nightlyDue`（本地 2–5 点 + ≥20h 门槛）10min 轮询 + 启动惰性双档；runAll = L1 refresh ×3 → L2 update ×3 → L3 update ×3，per-step 失败隔离。
- **注入**：`injectionBlockSync` 四槽全量拼接 + 剥脚注 → persona.ts 拼进 system prompt（"关于这个用户的长期记忆"）。**无查询相关性筛选、无 rune 预算**。
- **模型写**：save_preference 窄工具（仅 preferences 槽、显式、≤240 字、一次一条）。
- **测试**：229 全绿；时钟全注入（nightlyDue 纯函数）。

### 2.2 WeKnora 机制要点（事实，详见调研报告）

1. **条目模型**：memory_items 独立成行，kind（profile/preference/fact/task/interest）× status（active/superseded/archived/**pending**）× origin（explicit/extracted/manual）；矛盾用 **supersede 链**不删除（保留 invalid_at/superseded_by，可审计"记忆为何改变"）；手编即免疫后台覆盖。
2. **防复活**：墓碑表只存指纹（SHA-256）+ 源消息 id + 时间窗，用户删的蒸馏写不回来。
3. **推断确认**：inferred 条目进 pending，可见但**永不注入**。
4. **读路径零模型调用**：常驻块（profile/preference/interest ≤900 rune）+ 情境项（fact/task）词法召回（CJK uni+bigram，≤600 rune/5 条）→ `<user_memory>` 信封（声明"背景数据非指令"）→ system prompt 末尾。
5. **写路径防丢轮次**：每轮先落 pending 队列（数据性质），定时器只决定何时跑；水位线 extract_cursor 只在段成功后推进；在飞标记 + 10min 超时防 worker 崩溃卡死；去抖 90s + 最小间隔 300s；超限排 follow-up。
6. **提取 = 决策制**：单次 LLM 调用输出 `{memories:[{action:add|update|delete|none, target:索引, kind, topic, content, importance, source:行号, expires_at, inferred}], topics:[...]}`；候选旧记忆裁到 15 条（防无关记忆诱发虚假 update/delete）；truncate 重试一次；解析失败 fail-safe。
7. **每日整理**：合并近重复（词重叠/余弦门槛 + 模型裁决）、过期归档、陈旧任务（45 天）降级不删除。

### 2.3 领域差异与适配映射（WeKnora → OpenPrism）

| WeKnora | OpenPrism 适配 | 说明 |
|---|---|---|
| 多租户 SaaS，PostgreSQL + asynq 队列 | 单机 SQLite（node:sqlite 同步 API）+ **进程内调度器** | setTimeout 去抖 + pending 状态持久化（防重启丢任务）+ 启动恢复（在飞超时判定） |
| 记忆源 = 对话消息 | 记忆源 = **对话 + 账本 + 任务**（三 surface） | chat 走消息水位线；ledger/tasks 变更是结构化事件，保留 L1 指纹 diff 作变更检测（待裁决 §4-Q4） |

## 5. Innovate（已收口：方案 A）

### 方案 A：全盘条目化（推荐）

**核心**：以 WeKnora 条目模型为唯一记忆真相（新 4 表：memory_items / memory_tombstones / memory_meta(调度+整理状态) / 沿用 l1 两表），删 memory_slots/l2_entries/l2_meta/l3_meta；提取=决策制、触发=对话后 90s 去抖 + 夜间 consolidate；注入=分层召回纯函数。

- 优点：概念单一（"记忆=条目"），supersede/墓碑/pending/重要性/容量淘汰一次到位；注入可控（预算+相关性）；延迟达标；后续扩展（向量、检索条件化）有干净地基。
- 代价：db.ts 换轨 + memory-layers.ts 重写（~530 行 → 估计 ~700 行）+ Memory.tsx 改版 + 测试重写；一次性风险集中。
- 风险：提取决策制对模型能力要求高于"纯抽取"（需可用模型；fail-safe 必须严）。

### 方案 B：渐进（先延迟后模型）

一期只把 runAll 挂到对话后 90s 去抖（改 main.ts 调度 + 门控防重），条目化推二期。

- 优点：改动小（~100 行），三天内可用。
- 代价：槽文档模型的固有缺陷（全量注入、无 supersede、策展粒度粗）继续积累；二期来时一期代码大部分重写；两套触发语义并存期心智负担。

### 方案 C：仅延迟改造

等价于 B 的一期且不做二期承诺。不推荐：用户已明确"个人长期记忆挺重要"，欠账终要还。

**推荐 A**：三层上线仅 3 天、数据量小，换轨成本处于最低点；"个人智能记录"的差异化价值就在记忆质量，值得一次做对。

## 6. Plan（Detailed Design & Implementation）

### 6.1 数据模型（db.ts 新增 DDL + ensureColumn）

```sql
-- 记忆条目（唯一真相）：kind × status × origin 生命周期，supersede 链不物理删除
CREATE TABLE IF NOT EXISTS memory_items (
  uid           TEXT NOT NULL,
  id            TEXT NOT NULL,
  kind          TEXT NOT NULL CHECK (kind IN ('profile','preference','fact','task')),
  status        TEXT NOT NULL CHECK (status IN ('active','superseded','archived','pending')),
  origin        TEXT NOT NULL CHECK (origin IN ('explicit','extracted','manual')),
  topic         TEXT NOT NULL DEFAULT '',
  norm_key      TEXT NOT NULL,
  content       TEXT NOT NULL,
  importance    INTEGER NOT NULL DEFAULT 3 CHECK (importance BETWEEN 1 AND 5),
  source_ref    TEXT,
  valid_from    INTEGER NOT NULL,
  invalid_at    INTEGER,
  superseded_by TEXT,
  expires_at    INTEGER,
  last_used_ts  INTEGER,
  use_count     INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (uid, id)
);
CREATE INDEX IF NOT EXISTS idx_memory_items_key ON memory_items(uid, norm_key, status);
CREATE INDEX IF NOT EXISTS idx_memory_items_live ON memory_items(uid, status, importance, valid_from);

-- 墓碑：只存指纹与主题（不存原文），阻止蒸馏复活已删除记忆
CREATE TABLE IF NOT EXISTS memory_tombstones (
  uid         TEXT NOT NULL,
  fingerprint TEXT NOT NULL,
  topic       TEXT NOT NULL DEFAULT '',
  source_ref  TEXT,
  created_ts  INTEGER NOT NULL,
  PRIMARY KEY (uid, fingerprint)
);
```

- `memory_meta`（已存在）**扩列**而非新建：`extract_cursor INTEGER`（chat 水位线 = conversation_events.id）、`ledger_cursor INTEGER`（账本水位线 = ledger_entries.seq）、`tasks_fingerprint TEXT`（任务全量指纹）、`scheduled_ts INTEGER`（去抖计划时刻）、`in_flight_since INTEGER`（在飞标记，超时判死）、`last_extract_ts INTEGER`（最小间隔节流用）、`consolidated_ts INTEGER`（每日整理时钟）。经 `ensureColumn` 幂等补列；`last_run_ts/runs` 保留（nightly 整理沿用语义）。
- **旧表处置（2026-09-10 用户裁决：全部丢弃）**：`memory_slots`/`l2_entries`/`l2_meta`/`l3_meta`/`l1_entities`/`l1_changes` 六表**代码零引用**；不 DROP（SQLite 删表无收益，保留仅为回滚保险），迁移读一次后永久停读停写。
- SQLite 无 CHECK 的 UPDATE 约束问题：kind/status/origin 靠应用层枚举校验（与 WeKnora 同）。

  expireOverdue(uid): number;                                             // expires_at 到期 → archived
  archiveOverflow(uid): number;                                           // active>200 → importance→last_used→valid_from 确定性淘汰

  hasTombstone(uid, fingerprint): boolean;
  hasTombstoneForSource(uid, sourceRef, windowMs): boolean;               // 默认 1h 时间窗

export class MemoryExtractor {

**三 surface 新输入检测（全部原生，零 L1 依赖）**：

| surface | 检测机制 | 渲染为提取段 |
|---|---|---|
| chat | `conversation_events.id > memory_meta.extract_cursor`（join conversations 过滤 uid；user/assistant 文本消息） | 按 `(cid, 1h 静默)` 切段，≤40 行/段、≤3 段/次，超限置 truncated 排后续；行格式 `[n] (MM-DD HH:mm) 用户/助手: 文本`，前 4 行只读上下文 |
| ledger | `ledger_entries.seq > memory_meta.ledger_cursor`（**含 kind=void 行**——"作废了 X"也是有信息量的记忆事件；渲染时 void 行显式标注"已作废"） | 追加序即时间序，≤60 行/次；行格式复用旧 l1Live 的格式化逻辑（流水/计划/打卡/作废 四类行文本，搬进本文件为纯函数 `renderLedgerRow`） |
| tasks | `tasks_fingerprint = sha1(全量任务行规范串)`（任务量级小，全量比对；内容含 id/title/instruction/trigger/enabled/last_run_ts） | 指纹变化 → 全量任务清单作为一段（行格式复用旧 `describeTrigger` 逻辑），提取后更新指纹 |

**extractOnce 流程**（WeKnora Handle 的 SQLite 单机版）：

1. **收集新输入**（数据性质保证不丢）：按上表三 surface 取段；全空 → `no_new_input`。
2. **每段一次 LLM 调用**：输入 = 早前上下文 4 行（chat 段，只读）+ 已有条目 ≤15 条（词法相关性排序，无相关则 importance/新近前缀）+ 墓碑主题列表 + 编号 transcript（chat）或实体块（ledger/tasks，段头标注 surface 名："生活账本记录"/"提醒任务清单"）。
3. **决策 JSON**（WeKnora 决策制，中文 prompt）：
   ```json
   {"memories":[{"action":"add|update|delete|none","target":<已有条目索引|null>,
     "kind":"profile|preference|fact|task","topic":"短主题名","content":"一句话",
     "importance":1-5,"source":<行号>,"expires_at":"YYYY-MM-DD|null","inferred":true|false}]}
   ```
4. **applyDecisions**（应用层校验，非法即忽略该条）：
   - `add`：`insertItem`（内部完成净化→脱敏→墓碑（指纹 + source_ref 1h 窗）→norm_key 查重（同内容同键=幂等返回；包含式重复=短者丢弃/长者取代）→ inferred→pending）；
   - `update`：target 索引有效 → 旧条 `supersedeItem(uid, oldId, newId)` + 新条插入 active；
   - `delete`：target 有效 → 旧条 superseded + 墓碑（指纹=旧内容，topic=旧 topic）；
   - `none`/未知 action：忽略；truncate 检测 → 重试一次（预算 1200→4000 token）。
5. **成功段推进对应水位线**：chat 段成功 → `extract_cursor = 段末 event id`；ledger 段成功 → `ledger_cursor = 段末 seq`；tasks 段成功 → `tasks_fingerprint` 更新；**失败段不推进**（下次重读）。
6. **尾部**：`consolidateIfDue`（距 consolidated_ts ≥20h 才跑，rides along，不需要独立调度器）。

**触发点（谁调 notify）**：

- `conversations.send()` 尾部（`agent.whenIdle()` 后）→ `onTurnDone(uid)` 回调（deps 可选注入，main.ts 接 `extractor.notify`）；
- server.ts 账本/任务写路由（POST/PUT/DELETE /api/ledger*、/api/tasks*）→ fire-and-forget `notify(uid)`；
- **notify 只是延迟优化**：正确性由水位线/指纹的数据性质保证——未 notify 的变更（如 agent 工具写的账本）会在下一次任意触发或启动恢复时被 diff 到，不丢。

**main.ts**：

- 新增 `EXTRACT_CHECK_MS = 10s` interval：`dueUids(users)` → 逐 uid `runDue`（串行）；
- nightly interval 保留但内容改为：`nightlyDue`（**该纯函数从 memory-layers.ts 移植至本文件导出**）→ 对每 uid 跑 `consolidate`（不再 runAll）；

## 7. 风险与回滚

- **决策制对模型要求高**：fail-safe 三层——解析失败不推进水位线（重试）、非法 action/target 忽略、inferred→pending 不生效。最坏情况=模型差时记忆更新变慢，不会写坏。
- **LLM 成本上升**（90s 去抖 × 高频对话）：最小间隔 5min 节流；单段调用（非全量重喂）。
- **换轨一次性风险**：旧表保留不删、迁移幂等、`memory_slots` 停写不停读 → 回滚 = revert 代码即可回旧机制（旧数据未破坏）。
- **SQLite 单进程串行**：提取在 server 进程内异步跑，同步 DB 调用量小（百行级扫描），不阻塞请求路径（notify fire-and-forget）。

## 1. Requirements (Context)

- **Goal**: 任务通知的微信推送送达率最大化——token 过期时降级重试（tokenless），降级仍失败则入待补投队列，该用户下次任一入站消息到达时自动补发，站内兜底保持不变。
- **In-Scope**:
  - `src/app/ilink.ts`：`sendMessage` 空 contextToken 时请求体省略 `context_token` 键；`ret=-2` 抛新增的 `ILinkSessionStaleError`
  - `src/app/wechat-bridge.ts`：`pushToWechat` 降级重试与落待补投；`handle` 入站时补投；`unbind` 清理
  - `src/app/db.ts`：新表 `wechat_pending`
  - `test/app-wechat.test.ts`：上述行为的确定性用例
- **Out-of-Scope**:
  - 企业微信群机器人 webhook 等新通知渠道（「每天绝不断」的硬保证，另立 spec）
  - 回复链路（`handle` 末尾的回复推送）的行为变化——回复用的 token 刚从入站拿到必然新鲜，失败留日志的现状保持
  - 定时任务的调度、站内通知链路改动
- **Acceptance Criteria**:
  - [ ] AC1: 有缓存 token 的推送遇 ret=-2 时，自动以「请求体不含 context_token 键」的形式重发一次；重发成功即返回 true
  - [ ] AC2: 无缓存 token（从未对话）的推送直接以省略字段形式发送一次；失败不重试、直接落待补投（hermes #35062 教训：tokenless 失败再 tokenless 无意义）
  - [ ] AC3: 推送最终失败 → 通知文本（含 `【补投】` 前缀语义不变，存原文）入 `wechat_pending`；该用户下次任一入站消息到达时，在跑回合之前按入队顺序用新鲜 context_token 补发全部待补投，成功即删；单条失败即停、剩余保留
  - [ ] AC4: 现有行为不回归——绑定/扫码/轮询/回复/越权过滤/站内兜底不变；`ret=-2` 之外的错误路径不变（-14 仍走 expire）；解绑清空该用户待补投
  - [ ] AC5: `pnpm test` 全绿、`pnpm typecheck` 全绿

## 2. Research Findings

- **事实与约束（协议层）**:
  - iLink `sendmessage` 的 `context_token` 是会话路由锚点；服务端凭据约 11-15 小时无用户入站即失效（#309 实测），失效后带过期 token 发送被拒 `ret=-2 "prepare failed"`
  - 省略 `context_token` 字段（非空串）是被服务端接受的降级路径（hermes 文档实测「消息仍可送达」；ZCode 生产形态；QwenPaw 修复同款）——但会话被彻底回收时 tokenless 也失败（hermes "session not ready"）
  - 机器人出站消息不能给凭据续期（#309 keepalive 反例实测）；只有用户侧行为（入站消息）能刷新——所以补投挂在新入站上是协议内唯一可靠的恢复点
  - OpenPrism 现状：`ilink.ts:163-186` sendMessage 恒带 `context_token`（空串也是空串键）；ret=-2 走通用 Error
- **现状链路**:
  - 推送：`main.ts taskRunner` → `wechat.pushToWechat(uid, text)`（`wechat-bridge.ts:262`）→ 恒发 `bind.last_context_token ?? ""`；任何失败 catch 后返回 false（站内通知已由 `notifications.push` 先行落库，不丢）
  - 入站：`pollOnce → handle`（`wechat-bridge.ts:190`）→ 第一时间把 `msg.contextToken` 落 `wechat_binds.last_context_token` → 跑回合 → 回复推送
  - 绑定表：`wechat_binds(uid PK, bot_token_enc, ilink_bot_id, ilink_user_id, state, bound_ts, last_context_token, last_msg_ts)`；迁移走 `ensureColumn`（`db.ts:529`）
  - 测试：`test/app-wechat.test.ts` fakeILink fixture 按 URL 分发脚本响应、记录全部调用（含 body），`pollOnce` 可直接确定性驱动
- **风险与不确定项**:
  - ret=-2 语义不区分 errmsg：hermes 只把 `prepare failed` 的 -2 视为会话过期（其余 -2 是限流）。本 spec 决策：一律按会话过期处理并降级重试一次——若实为限流，重试一次失败后落补投，与现状持平，无额外伤害（一次多余请求）
  - tokenless 降级的成功率无官方保证（灰色地带概率生还），验收以「重试请求确实发出且形态正确」为准，送达与否属服务端行为
  - 补投消息与站内通知天然重复（一个进微信、一个进提醒页）——现有「加推」语义本就如此，可接受

- `src/app/wechat-bridge.ts`:
  - 新增 `enqueuePending(uid, text)`（INSERT + 按 uid 只保留最近 50 条）
  - `pushToWechat` 重写推送体：第一次带 `last_context_token ?? ""` 发送；若第一次带了非空 token 且抛 `ILinkSessionStaleError` → 去掉 token（空串）重发一次；两次任一成功返回 true；第一次本就无 token 而失败、或降级重试失败、或其他错误 → `enqueuePending` 后返回 false；`ILinkTokenExpiredError`(-14) → 调 `expire(uid)`（与 getUpdates 同语义，快速置过期）再 `enqueuePending` 返回 false
  - 新增 `flushPending(uid, bind, contextToken)`：按 `id` 升序取该 uid 全部待补投，逐条 `sendMessage(botToken, ilink_user_id, contextToken, \`【补投】\${text}\`)`，成功即 DELETE 该行；任一条失败即停（剩余保留，留 error 日志）
  - `handle`：落 `last_context_token` 之后、`ensureFeed` 之前调 `flushPending(uid, bind, msg.contextToken)`
  - `unbind`：`DELETE FROM wechat_pending WHERE uid = ?`
- `test/app-wechat.test.ts`: 新增用例（见 §4.3 第 7-9 条）

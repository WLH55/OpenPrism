## 1. Requirements (Context)
- **Goal**: 手动压缩两条入口都可用：聊天里对 AI 说「压缩一下上下文」，AI 调用 compact 工具安排压缩；输入框发送 `/compact` 直接触发，不经过 AI
- **In-Scope**:
  - harness：`Agent.requestCompact()`——回合内设置标志，driver 在回合结束间隙执行强制压缩（复用 `compactConversation(force)`）
  - app：compact 工具注册（AI 可调用）+ `compactNow(uid, cid)`（HTTP 入口：空闲校验 + `agent.compact()`）
  - HTTP：`POST /api/conversations/:cid/compact`
  - 前端：输入框精确匹配 `/compact` 拦截（不落用户消息），调接口，结果用 banner 提示
  - 前端：SSE `compaction` 事件处理——两条入口的压缩结果统一走横幅提示（工具路径的压缩发生在回合结束后，接口无法同步返回结果）
- **Out-of-Scope**:
  - 自动压缩阈值与遮蔽算法（不动，`compactConversation` 原样复用）
  - 压缩参数定制（保留比例、摘要上限——均走缺省）
  - 微信桥入口（微信侧用户说压缩也会走 AI 工具路径，天然覆盖，不做微信专控命令）
- **Acceptance Criteria**:
  - [ ] AC1 对 AI 说压缩类指令 → AI 调用 compact 工具 → 本回合结束后日志出现 `compaction/summary` 事件，下一回合投影 = 摘要 checkpoint + 尾部原文
  - [ ] AC2 输入框发送 `/compact`：不产生 user/message 事件，压缩执行，界面提示压缩完成
  - [ ] AC3 会话太短（无可压缩区间）：两条入口都得到可读说明（「会话还太短，暂时没有可压缩的内容」量级），无半成品事件
  - [ ] AC4 AI 正在回复时发 `/compact`：明确提示稍后再试（HTTP 层拒绝，不排队不静默）
  - [ ] AC5 压缩失败（如 shrink 校验失败）时错误可见，agent 驱动不死，后续回合正常
  - [ ] AC6 AI 工具路径压缩完成时，界面显示压缩成功提示（SSE `compaction ok:true` → 横幅）；失败时同样横幅可见（`ok:false` → 失败原因）
  - [ ] AC7 `pnpm test` + `pnpm typecheck` + `pnpm build:web` 全绿

## 2. Research Findings
- **事实与约束**:
  - `Agent.compact()` 已存在：`src/harness/core/agent.ts:446-462`，要求 `status === "idle"`（否则抛错，注释指向设计 §12 差异 6「无 maintenance phase 独立态——简化，可后补」）、`force: true` 绕过阈值。app 层与前端从未调用。
  - 工具在回合内执行时 agent 处于 running 状态，直接调 `compact()` 必然抛错；且摘要期间日志在变会触发 `compactConversation` 的稳定性检查放弃提交（`compact.ts:159-164`）。因此工具触发的正确语义 = 设置标志、回合结束后由 driver 在回合间隙执行（此时 `turn/end` 已落、日志稳定、status 仍为 running，不与 compact() 的 idle 检查冲突）。
  - driver 循环现成间隙：`agent.ts:383-406` `while (inbox...) { await runTurn() }`——`runTurn()` 之后、下一轮条件检查之前是天然挂点。
  - 压缩执行防护已齐：`runCompact` 有 `compacting` 防重入（`agent.ts:150-158`）；失败走 emit `compaction ok:false`（`maybeCompact` 同款，`agent.ts:169-176`）。
  - agent 池化：`src/app/conversations.ts:224-227`（`pool` Map + `assembling` 防并发装配）。装配函数内 tools 先于 createAgent 存在——compact 工具 handler 用延迟引用（闭包 `let agentRef`，createAgent 返回后赋值），池化保证同一会话复用同一实例。
  - 前端无既有斜杠命令机制（grep `slash|command` 零命中）；输入框提交处为唯一拦截点。
  - `compactConversation` 两个可预期失败：区间不足（`nothing compressible`，`compact.ts:153`）与 shrink 校验（`compact.ts:169-173`）——错误信息为英文内部口径，HTTP 层需转可读中文。
  - SSE 已转发 `compaction` 实时事件（`agent.subscribe` → stream，`server.ts:616-647`）；前端 `Chat.tsx:350-402` 的事件分支不处理该类型（现状被忽略）——本 spec 补此分支，工具路径的压缩结果经此到达界面。事件顺序有保障：`turn-end`（横幅清空）先推，`compaction`（横幅置压缩结果）后推（driver 在 `runTurn()` 返回后才执行压缩），同一 SSE 流按序到达。
- **现状链路**: 自动压缩 = 每 step 请求前 `maybeCompact` 阈值触发；手动 = 无入口。本 spec 补两条手动入口，均收敛到同一个 `compactConversation`。
- **风险与不确定项**:
  - 压缩吞注入：若手动压缩遮蔽最后一条带 context 的用户消息，回合注入随区间被摘要吞掉——既有边缘口径（前缀缓存 spec 已记录），复用不新增处理。
  - 回合间隙压缩与排队消息：压缩后 inbox 若有排队 followup，下一 turn 以新投影开始，语义正确。
  - 工具承诺与实际结果的时间差：工具立即返回「已安排」，压缩在回合结束后才执行，失败只能经 compaction 直播事件可见——AC5 口径。

## 3. Innovate (Optional: Options & Decision)
### Option A 双入口（AI 工具 + /compact 命令）
- 内容: harness `requestCompact()` 回合间隙机制 + app compact 工具 + HTTP 接口 + 前端命令拦截
- Pros: 用户两种使用习惯都覆盖；命令入口零 token 成本直达；工具入口覆盖微信桥（微信里说压缩同样生效）
- Cons: 触达 harness 与前后端四层
### Option B 仅 AI 工具
- 内容: 只注册 compact 工具（依赖 harness 间隙机制）
- Pros: 改动面小一条链
- Cons: 输入框命令形态缺失；用户想绕开 AI 直接压缩时无路径
### Option C 仅命令 + HTTP
- 内容: 只做 /compact + POST 接口（复用已有 `agent.compact()`，harness 零改动）
- Pros: 不动 harness
- Cons: 「跟 AI 说」的路径缺失，微信桥无法触发
### Decision
- Selected: Option A
- Why: 用户原话同时给出两种形态（「直接跟ai说 或者提供一个命令」）；工具路径顺带覆盖微信桥；harness 间隙机制即设计文档预告的后补项

- Reason: 三个成立方案的范围决策，需明示

## 1. Requirements (Context)

- **Goal**: 用户在任何通道（网页/微信机器人/定时任务）与助手交互时，"今天/本周/本月"按**用户档案里的时区**计算；档案值由浏览器自动上报，且可在个人资料页手动修改。
- **In-Scope**:
  1. 用户档案存 `tzOffsetMinutes`（分钟，东八区=480）：users 表加列（迁移）+ UserRecord 字段 + PATCH /api/profile 更新。
  2. 浏览器自动上报：web 前端在已带 tz 的请求外，启动/刷新时静默上报当前浏览器偏移（服务器端幂等更新，值相同不写库）。
  3. 个人资料页（Profile.tsx）加时区显示与修改：下拉常用时区（UTC-12~+14 整点档 + 当前浏览器值）+ 保存。
  4. `createLedgerTools` 加 `tzOffsetMinutes` dep：today/goals 视图、flows 的 from/to 日期过滤（dayKey）从 UTC 改为档案口径。
  5. `ConversationStore` 组装时 `tzOffsetMinutes` 从用户档案读（按 uid），替换现状"缺省服务器本机"；main.ts 宿主接线。
  6. persona 日期注入（已有 tzOffsetMinutes 通路）与 tasks 触发时刻解释同吃档案值（不改代码路径，只改来源）。
- **Out-of-Scope**:
  - IANA 时区名 / DST 自动换算（存偏移分钟；DST 变更靠浏览器下次打开自动刷新覆盖）。
  - 微信侧任何时区逻辑（读档案即可，无通道级工作）。
  - UI 各页已传 tz 的既有请求（保持现状，它们与档案口径一致后无感）。
- **Acceptance Criteria**:
  - [ ] AC1 档案存取：PATCH /api/profile { tzOffsetMinutes } 持久化；GET /api/me 返回该值；非法值（非整数/超 ±840）400。
  - [ ] AC2 自动上报：前端加载后浏览器偏移写入档案（测试 mock 或实现内省验证）；值未变不产生写库。
  - [ ] AC3 个人资料页可改：下拉选择 + 保存生效（UI 实现；手验）。
  - [ ] AC4 工具层口径：tz=480 档案下，query_ledger what=today 的 date/成员按东八区"今天"折叠（UTC 23:00 记的流水在东八区次日的 today 里可见）；flows from/to 同口径。
  - [ ] AC5 微信/任务同源：ConversationStore 组装读档案值（单测注入档案值断言 createLedgerTools 收到）；tasks 触发时刻解释用档案值。
  - [ ] AC6 `pnpm test` + `pnpm typecheck` 全绿；web build 通过（Tasks.tsx 外部错误除外，见上份 spec §7 偏差 5）。

## 2. Research Findings

- 事实与约束:
  - `ConversationStore` deps 已有 `tzOffsetMinutes?(): number`（conversations.ts:45），当前接了 taskTools 触发解释（:481）与 persona 日期注入（:543）；**createLedgerTools（:450）未传**——query_ledger 的 today/goals 在 tools.ts 内固定 UTC（tzOffsetMinutes=0）。
  - 缺省取服务器本机（`-new Date().getTimezoneOffset()`）——部署机器时区 ≠ 用户时区，微信/纯 API 场景下口径错。
  - `UserRecord`（auth.ts:39）现无时区字段；Profile.tsx 已有 updateProfile 通路（emoji/color/avatar）——加 tz 顺路。
  - web 各页已用 `-new Date().getTimezoneOffset()` 作为请求 tz（api.ts:265 等）——UI 视图口径已是浏览器时区，本次统一后 agent 与 UI 一致。
  - users 表迁移模式：migrate.ts 已有列演进先例（执行时按现状核对）。
  - **并行改动警告**：工作区有另一会话在推进（tzOffsetMinutes 骨架疑为其工作）；执行前须重查 conversations/auth/server 现状，冲突则合并口径。
- 现状链路: server.ts 组装 ConversationStore deps（宿主接线点）；ledgerFor 按 uid——tz 读取应同为按 uid 的同步/异步查档案。
- 风险与不确定项:
  - tzOffsetMinutes 是函数（装配时求值一次）vs 用户改档案后旧值——接受回合粒度刷新（systemPrompt 每步重取的同款取舍）。
  - 浏览器静默上报的触发点（前端 App 挂载 / api.request 惰性附带）执行时定，原则：一次/会话，幂等。
  - DST 地区偏移漂移：浏览器每次打开刷新覆盖；微信长期不用网页的用户最多漂一小时档，接受（记 Follow-up）。

## 3. Innovate (Optional: Options & Decision)

### Option A
- 方案: 存偏移分钟数（tzOffsetMinutes），浏览器自动上报刷新，Profile 可手改。
- Pros: 与现有 dayKey/localParts/TZ 注入体系零新依赖；DST 靠刷新覆盖；改动小。
- Cons: 不含 DST 规则——夏令时切换后未打开网页的用户档案偏移过时。
### Option B
- 方案: 存 IANA 时区名（如 Asia/Shanghai），折叠层引入时区规则库换算。
- Pros: DST 自动正确。
- Cons: 引入运行时依赖或自带规则表（违背零运行时依赖倾向）；fold 全注入点改签名；改动面大。
### Decision
- Selected: Option A（个人应用 + 浏览器高频打开的现实下，偏移分钟 + 自动刷新已覆盖 99% 场景）。
- Why: 用户确认的方案即"档案+可改"；A 是该意图的最小正确实现。
